# Dashboard and `jky-store` — Design Spec

**Date:** 2026-08-27
**Implements:** v0.1 build-order step 5, success criterion 5
**Supersedes nothing.** Extends `2026-08-26-jky-terminal-v0.1-design.md`.

---

## 1. Purpose

A workspace section that holds the things a person keeps beside their work:
notes, todos, a calendar, reminders, and upcoming events — plus email alerts
that reach them when the app is closed.

The governing rule, stated by the user and taken literally throughout:

> nothing gets removed until the user removes it

There is no pruning, no cap, no expiry, and no "tidy up old items" pass
anywhere in this design. The assistant prunes conversations at five; this
subsystem deliberately does not, because a note you wrote in March is not
less yours in August.

---

## 2. What is being built, and what is not

### Phase A — the store and the dashboard

`jky-store` plus a Dashboard section containing Notes, Todos, Calendar,
Upcoming Events, Reminders and Quick Actions. Everything persists to disk
and survives restart, reinstall of the frontend, and force-quit.

### Phase B — email alerts

SMTP delivery, a schedule, and OS-level registration so alerts fire with the
app closed.

Phase A ships first and is useful alone. Phase B depends on events existing,
so it cannot come first.

---

## 3. The constraint on "even if terminal is off"

The requirement is that an alert arrives before an event even when JKY
Terminal is not running. This is achievable, with one boundary that must be
stated plainly rather than discovered later:

| Situation | Alert arrives? | Why |
|---|---|---|
| App open | yes | The app itself checks. |
| App closed, computer on and logged in | yes | An OS-scheduled helper checks. |
| Computer asleep | on wake | The OS runs missed timers when it wakes. |
| **Computer off** | **no** | Nothing local is running. There is no way around this without a server that holds your mail credentials, which this project does not have and should not have. |

Anything claiming otherwise for a local-only app is claiming something false.
If mail must arrive with the machine off, that requires a hosted relay — a
separate product decision with real cost and real custody-of-credentials
implications, deferred out of v0.1.

### The mechanism

A small helper, registered with the OS at the moment the user enables alerts:

| Platform | Registration |
|---|---|
| Linux | systemd **user** timer (`~/.config/systemd/user/`) |
| macOS | launchd **LaunchAgent** (`~/Library/LaunchAgents/`) |
| Windows | Task Scheduler entry via `schtasks`, current user |

All three are per-user, need no administrator rights, and are removed when
the user turns alerts off. The helper reads the same events file the app
writes, sends anything now due, and records what it sent so a restart does
not send twice.

### Gmail credentials

Gmail rejects account passwords for SMTP; it requires an **app password**
generated by the user with 2FA on. That app password is a secret and goes to
the OS keychain through the existing `jky-secrets` path — never to the
settings JSON, never through the frontend, never into the audit log. It is
governed by exactly the same rule as an API key: the app can store it, check
that it exists, and delete it. Nothing reads it back out to the UI.

## 4. Data model

Four collections, four files, in the app data directory beside `settings.json`.

Separate files rather than one, so a corrupt or partially-written collection
costs the user that collection instead of everything they have ever saved.

```
notes.json      Note[]
todos.json      Todo[]
events.json     Event[]
reminders.json  Reminder[]
```

```rust
struct Note {
    id: String,          // "note-<millis>-<counter>"
    title: String,       // first line of the body, or "Untitled"
    body: String,
    created_at: String,  // RFC 3339, UTC
    updated_at: String,
}

struct Todo {
    id: String,
    text: String,
    done: bool,
    created_at: String,
}

struct Event {
    id: String,
    title: String,
    starts_at: String,           // RFC 3339, UTC
    colour: EventColour,         // one of six named tokens, not a hex string
    alert_minutes_before: Option<u32>,  // None = no email
}

struct Reminder {
    id: String,
    text: String,
    at: String,     // "HH:MM", local wall clock — a daily checklist, not a date
    done: bool,
}
```

### Why `colour` is an enum, not a hex string

The mockup's event dots are red / blue / green / amber / violet / cyan. Stored
as hex, they would be wrong in six of the seven themes and unreadable in High
Contrast. Stored as a name, each theme resolves it to its own palette.

### Times

Stored UTC, rendered on the reader's clock — the same rule the activity log
now follows, and for the same reason: an event at `19:30Z` is tomorrow
morning for this user, and storing local time makes a laptop that crosses a
timezone start lying about when things happen.

`Reminder.at` is the exception and is a local wall-clock `HH:MM`, because
"07:00 morning exercise" means seven in the morning wherever you are.

## 5. `jky-store` crate

```
crates/jky-store/src/
  lib.rs        re-exports, StoreError
  model.rs      the four types, id generation, validation
  collection.rs generic load/save/insert/update/remove over a JSON file
  store.rs      Store: one handle over the four collections
```

`collection.rs` is generic over `T: Serialize + DeserializeOwned + Identified`,
so notes, todos, events and reminders share one tested implementation of
"read a JSON array from a file, mutate it, write it back atomically" instead
of four near-copies.

### Durability

Every write goes to a temporary file in the same directory and is renamed
into place, matching `jky-settings`. A write interrupted by power loss leaves
the previous file intact rather than a half-written one.

### Missing and corrupt files

A missing file is an empty collection, not an error: a first run is not a
failure. A corrupt file **is** an error and is surfaced, not silently reset —
quietly replacing unreadable data with `[]` is how a user loses everything
and is told nothing.

## 6. IPC surface

New Tauri commands, added to the pinned list in `tests/security.rs`:

```
store_list_notes / store_save_note / store_delete_note
store_list_todos / store_save_todo / store_delete_todo
store_list_events / store_save_event / store_delete_event
store_list_reminders / store_save_reminder / store_delete_reminder
```

Twelve commands, three per collection. `save` covers create and update: the
frontend sends a whole record, and an id it has not seen before is an insert.
This keeps the surface small and makes the frontend's job idempotent.

No command reads a secret, and no command takes or returns a `Secret<_>`, so
the two existing security assertions continue to hold unchanged.

## 7. UI

### Navigation

Dashboard joins the rail. Inside it, a sub-section list on the left in the
same shape as the assistant's conversation list, because the user asked for
that pattern by name:

```
Overview      the widget grid
Notes         a list of every saved note, and an editor
Todos
Calendar      month grid
Reminders
Mail Alerts   Phase B
```

Each panel wears the shared `PanelHead`, so the dashboard's sub-sections look
like the settings panels rather than a third style.

### Overview

The widget grid from the reference: Notes preview, Calendar, Reminders,
Upcoming Events, Email Alerts status, Quick Actions. Every widget is a live
view of the same store the dedicated panels write to — not a copy.

### Notes

The pattern the user pointed at: a list of saved notes down the side, one
open in an editor, with new and delete. A note is never dropped for age or
count. Deleting asks first, because a note is not recoverable once gone.

### Empty states

Every panel has one, and each says what to do rather than that there is
nothing — an empty dashboard on first run is the first thing a new user sees.

## 8. Testing

| Layer | What is proven |
|---|---|
| `jky-store` unit | round-trip, atomic write, missing file is empty, corrupt file is an error, delete removes exactly one, save-with-new-id inserts, save-with-known-id updates |
| Security assertion | the twelve new commands are on the pinned list; none is getter-shaped for a secret |
| Frontend unit | store adapter, calendar month maths (leap years, month boundaries, week alignment), upcoming-event ordering and filtering |
| a11y | every dashboard panel under axe, in all seven themes |
| Contrast | the six event colours against every theme's ground |
| Parity | the browser mock and the native adapter expose the same store surface |

The calendar deserves specific mention: month grids are a classic source of
off-by-one bugs at month boundaries, in leap years, and in the leading and
trailing days of the grid. That maths goes in a pure function with its own
tests, not inside a component.
